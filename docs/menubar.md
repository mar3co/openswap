# Menu bar extra

Entry: `openswap menubar` → `openswap.menubar.run`. Optional extra: `rumps`.

## Process

LaunchAgent `com.opensoft.openswap.menubar` runs `openswap menubar`. Accessory activation policy (no Dock icon). `NSApp.appearance` is left `None` so the extra inherits System Settings → Appearance.

`launch_agent.resolve_program()` picks what the plist runs. In the cask's app it is the in-bundle `OpenSwap.app/Contents/MacOS/OpenSwap`, not the `openswap` symlink Homebrew puts on PATH: the app path survives `brew upgrade` (the cask's postflight kickstarts the agent onto the new build), and launchd starting the bundle binary keeps the LaunchServices identity notifications need. A source install pins the uv console script `~/.local/bin/openswap`. The frozen app started with no arguments and no terminal (Finder, `open`) runs the extra.

### One extra at a time

`menubar.run` takes an exclusive `flock` on `<backup_root>/menubar.lock` (`menubar_instance.claim`) before the status item, timers or engines exist, holds it for the life of the process, and writes its pid into it (`lock_holder_pid`; the file is opened without truncating, so a copy that loses the race cannot erase it). The launchd job (`XPC_SERVICE_NAME` is the label, `launch_agent.runs_as_login_item`) is the copy that should run: it waits up to 10 s for the lock, because during a hand-over it starts while the old copy is still quitting, then exits 1 and launchd's `KeepAlive` retries it. If its plist is gone by then (Open at login was turned off) it calls `unload_own_job()` and exits 0 instead, so a `kickstart -k` from the cask cannot leave it restarting behind another copy. Any other copy (Finder, Spotlight, `open -a`, `openswap menubar`) does not wait for the lock: it leaves a show request, prints `OpenSwap is already running in the menu bar.`, and exits 0 once the holder takes the request. The holder may be between Quit and exit, and then nobody answers and its clean exit is not restarted, so for up to 2 s the copy also tries the lock again and runs if it comes free (its own request then opens its popover). A lock file that cannot be opened logs a warning and the extra runs unguarded.

A show request (`menubar_instance.leave_show_request`) writes `<backup_root>/menubar.show-request`, then posts the distributed notification `com.opensoft.openswap.menubar.show`. The lock holder consumes the file (`consume_show_request`) on that notification and once its popover and observer are attached at start-up, and opens the popover when the file is under 30 s old (`MenuBarApp._on_show_request`). Consuming deletes it, so one request opens the popover once whichever path gets there first. The file carries the request across the moments a notification alone would miss: a holder that has the lock but no observer yet, or a launchd copy that has not started. A reopen event (`applicationShouldHandleReopen:hasVisibleWindows:`, added to rumps' app delegate before `App.run` sets it) opens the popover directly (`MenuBarApp.show_popover`; before the popover attaches it opens once it does).

A copy launchd did not start that gets the lock while the login item runs this program (`launch_agent.login_item_runs_this`) hands over to it (`menubar_instance.hand_over_to_login_item`). That is the case after Quit, since `KeepAlive: {SuccessfulExit: false}` does not restart a clean exit; without it the Finder copy would keep the lock and the cask's upgrade kickstart would start a launchd copy that waits behind the old build. It leaves a show request, starts the job (`launch_agent.start_login_item`; a job that is already running this program, starting up or waiting for the lock, is not started again) and exits 0 once launchd has a pid, which frees the lock. A terminal `openswap menubar` prints that it started the login item and where its log is. If the hand-over fails it is logged and this copy runs; a job `start_login_item` could not start is booted out first (it is not this process), so a start launchd only delayed cannot come up later behind this copy's lock, while the plist and the recorded failure stay. A login item that is running holds the lock, so it gets a show request instead and is never started again.

`start_login_item` kickstarts a loaded job only when the program launchd loaded (the `arguments` `launchctl print` reports, `status()["program"]`) is the plist's `ProgramArguments`: launchd keeps the definition it loaded, and `set_login_item` or the migration may have changed the plist under it, so a kickstart would start the old program and this copy would hand over to it. When they differ, or `print` does not say, it boots the job out (it is not this process), waits for it to unload and bootstraps the plist, as `install()` does; a job that is not loaded is bootstrapped. The job may still be unloading: the start-up migration boots out a uv extra just before (it waits for that bootout itself, and keeps the uv plist when the extra has not stopped), so when the first start fails or no pid appears within 5 s it waits for the job to unload and bootstraps once more. A running job counts only when its loaded program is confirmed to be the plist's (`running_login_item_pid`); an unreported program is reloaded too, since the pid could be an old executable. A start that still fails is booted out again if launchd kept it loaded (a late start would only wait behind this copy's lock), and its time and launchctl's detail go to `<backup_root>/login_item_status.json` (`last_start_failure`). Any start that works clears the file, and so does the launchd job when it starts.

`openswap setup` and `menubar --install-service` start the job with `install()` from outside any extra. An extra launchd did not start (opened from Finder while Open at login was off) may still hold the lock, and the new job would loop behind it. So once launchd has a pid they leave a hand-over request (`menubar_instance.hand_over_from_cli`): `<backup_root>/menubar.handoff-request`, then the distributed notification `com.opensoft.openswap.menubar.handoff`, read like a show request (`MenuBarApp._on_handoff_request`, on the notification and at attach). That extra runs the start-up check again (`login_item_waiting`): when its login item runs its program and launchd's copy is up, it leaves a show request and quits. The CLI then waits up to 15 s for the pid in `menubar.lock` to be launchd's, and only then prints `OpenSwap is running in your menu bar and starts at login.` If a live copy still holds it, it warns that OpenSwap is still running outside its login item and says to quit it from the menu bar.

### Open at login

Settings › General › **This Mac** › **Open at login** is on when the LaunchAgent plist exists (`launch_agent.login_item_enabled`, read each time the page is built); there is no stored preference, so `setup`, `uninstall`, `brew uninstall` and the switch always agree. While it is on, `login_item_status.json` records a failed start, and this copy is not the launchd job, a warning row follows it: **macOS isn’t starting OpenSwap at login** with **Open Login Items** (`x-apple.systempreferences:com.apple.LoginItems-Settings.extension`), so the switch never claims to work when macOS refused the last start. That holds whatever the cause (a start-up hand-over or the switch). The controller calls `launch_agent.set_login_item` on a worker thread (`MenuBarApp._apply_login_item`; the switch is disabled meanwhile) and the 1 s tick applies the result. What it does depends on the caller:

| Caller | On | Off |
|---|---|---|
| The launchd job | Writes the plist when it is missing or runs another program (`"enabled"`, else `"unchanged"`); no `launchctl` | Deletes the plist (`"disabled_after_quit"`): this copy runs until Quit or logout, and a hint says it will not open at the next login. Quit then calls `unload_own_job()`, which starts `launchctl bootout` for the job in a new session and returns before the extra exits, so nothing is left loaded. A plain Quit with login on leaves the job loaded for the next login |
| Any other copy | Writes the plist and starts the job (`start_login_item`, which reloads a job still loaded from a plist this replaced; `"handoff"`); the copy then quits and launchd's copy takes the lock | Boots out a loaded job and deletes the plist (`"disabled"`) |

The call never boots out the calling process. From an `/AppTranslocation/` or `/Volumes/` copy it refuses (`Move OpenSwap to Applications first.`) and the switch is disabled with a hint; a uv install beside the cask will not turn it on (`bundle.refuse_uv_beside_cask`). A start that fails raises `LoginItemNotStarted`, and the warning row shows it. A uv install pins its console script, as `setup` does. `openswap setup` and `menubar --install-service` keep using `install()`, and `setup` waits for the pid through the same `launch_agent._wait_for_pid`.

### First run

The app and `openswap setup` are two ways to the same setup: both write the one login item, the LaunchAgent above, through `launch_agent`; neither stores a separate "open at login" flag.

- From a terminal, `openswap setup` saves the live Claude login and installs and starts the agent. In the app it prints the Edit Widgets hint in place of `openswap widget --install`, since the app registers its widget itself ([widget](widget.md#cask-app-bundle)).
- From Finder, the frozen app shows a welcome page. An LSUIElement app has no window, so a first launch would otherwise look like nothing happened. When the popover attaches, `welcome_on_start` decides: if `MenuBarSettings.welcome_done` is false, the app runs from a stable location, and the login item does not already run this app (`launch_agent.login_item_runs_this`), the popover opens by itself on `WELCOME_PAGE`. If the plist does run it (`openswap setup` ran), `welcome_done` is saved and nothing shows. A uv install never shows it.
- The page (`welcome_page_model`) has one line on what OpenSwap does, the Claude empty state (**Sign in with Claude**, **Save current login**) while there are no Claude accounts, an **Open at login** switch that starts on, and **Continue**; its header keeps More, so Quit stays in reach. Nothing is written before Continue. Continue saves `welcome_done`, then sets the login item to the switch through the same path as the Settings switch (`_apply_login_item`, above); a hand-over to launchd's copy is the last thing. With the switch off it only turns off a login item that runs this app (`login_item_runs_this`), so a plist for another copy is left alone. A failure is also shown as an alert, since Continue went on to the cards, where the hint under the Settings switch would go unseen. Closing the popover without Continue changes nothing: every open starts on the welcome page until Continue. From a translocated or mounted copy the switch is off and disabled with a hint to move the app to Applications, and Continue pins nothing and does not save `welcome_done`, so the copy in Applications welcomes again.

Settings › General ends with **This Mac**, what setup does from a terminal: **Open at login** (above), the **Claude Code status line** toggle (`claude_status_line`; its value is `statusline.is_installed`, read when the page is built, and both it and `openswap statusline --install/--uninstall` call `statusline.set_installed`, which pins `paint_command()`; from a translocated or mounted copy turning it on is disabled with a hint, and `set_installed` refuses it too, since the pinned path would disappear, while turning it off stays possible), and, in the app at a stable location, the hint "Add the widget: Edit Widgets, search OpenSwap".

### Moving from a source install

`openswap setup` (before it installs the login item, so the app it then bootstraps never races a half-migrated Mac) and the frozen extra's start-up run `bundle.migrate_from_uv_install` (idempotent; each step logs and continues on failure). It does nothing from a copy that runs from an `/AppTranslocation/` path (a quarantined app opened in place) or under `/Volumes/` (a disk image): those paths vanish.

1. The older `com.cswap.menubar` agent is booted out and its plist removed, whenever it is there.
2. A menu bar plist that runs the uv install (`ProgramArguments[0]` is a console script or interpreter, unreadable, or a copy of the app that no longer exists) is rewritten to the bundle executable. A plist on another copy of the app that still exists (the cask's, while a copy from Downloads or a dev build runs) is left alone. The plist is never re-bootstrapped here: opened from Finder or a terminal, the uv extra is booted out and this extra keeps running; running as that agent (`XPC_SERVICE_NAME` is the label), it leaves itself alone. The next login starts the app. The bootout is waited for (up to 5 s) before the plist is rewritten; if the uv extra is still stopping, the uv plist stays and the step fails for this start, so the start-up hand-over cannot mistake the dying uv extra for the app and quit.
3. The Remote tasks worker plist (`com.opensoft.openswap.worker`), when it runs the uv install by the same rule, gets the bundle executable with its own `worker …` arguments and other keys kept, and PATH led by the bundle's directory. A loaded worker is booted out and bootstrapped again on the app (unless this process is the worker); one that is not loaded starts from the app next time.
4. A Claude Code status-line hook (`statusLine.command` in Claude's `settings.json`) that names another openswap path is pointed at the bundle executable (any prefix before it is kept; the wrap state is untouched). A bare `openswap statusline` and a link to the app are left alone. In the app, `statusline --install` writes the bundle executable too.
5. The old widget host is retired (see [widget](widget.md#moving-from-a-source-install)).
6. An `openswap` that is not a link to the app, in uv's tool bin directory (`UV_TOOL_BIN_DIR`, `XDG_BIN_HOME`, `XDG_DATA_HOME/../bin`, `~/.local/bin`), `UV_INSTALL_DIR`, or anywhere on PATH, is reported once: `An older uv install is still on PATH: run uv tool uninstall openswap`. If a step above failed and the login item, worker, or status line still runs another openswap, the report names it and says to keep the uv tool until it is moved instead. The uv tool and `~/.openswap` are not touched.

`openswap upgrade` in the app runs nothing: it prints `brew upgrade --cask openswap` (or the release page for a copy Homebrew did not install).

The other way round, a uv `openswap` that comes first on PATH would undo the move. When the cask is installed (an `openswap` Caskroom exists under `/opt/homebrew` or `/usr/local`; checked on disk), the uv install's `setup`, `upgrade`, `uninstall`, `widget --install`, and `menubar --install-service` refuse (`bundle.refuse_uv_beside_cask`), naming `<prefix>/bin/openswap` and `uv tool uninstall openswap`. Its other commands still work, and a source install on a Mac without the cask is unaffected.

Uninstalling: the cask's `uninstall script:` runs `OpenSwap uninstall --homebrew-hook`. Homebrew runs a cask's uninstall stanza on `brew upgrade` and `brew reinstall` too, before it swaps the app, and it runs the installed copy of the cask, so a release's stanza is what runs when upgrading away from it. An `uninstall launchctl:` would therefore drop the login item on every upgrade. Instead the hook reads the brew command from its parent processes (`uninstall.homebrew_command`: the first word after `brew.rb`) and does nothing unless it is `uninstall` (`rm` and `remove` arrive as `uninstall`). On an uninstall it runs `uninstall.remove_integrations(force=True)`: the menu bar agent and the worker go when their plist runs this app or a program that is gone (a uv install's, a dev build's or another existing copy's stay), the worker through `disable_worker` (booted out anyway if it will not stop, since the app is about to go), the status line is restored when it names this app (a bare `openswap statusline` was written by a uv or source install and stays), and the appex is unregistered. With `--zap` among brew's arguments it also deletes the `openswap` and `claude-swap` Keychain items and each session profile's hashed item (before the files go, since its name comes from the profile's path); the `zap` stanza trashes the files. `zap` does not list the worker's label: `launchctl:` removes a job by label alone, and a uv install's worker shares it. Like `purge`, a zap also deletes the pre-XDG `~/.claude-swap-backup` (not on the cask's `zap` list, so the app removes it) and never deletes the Keychain item of a session profile Claude still runs on; profiles are found in every folder the zap deletes. `openswap uninstall` does the same removal, then execs `brew uninstall --cask [--zap] openswap`, whose hook finds nothing left; with `--zap` it refuses up front while a session-mode Claude is running or a profile's session records cannot be read, then, after the prompt, runs `purge` itself (`assume_yes=True`), which checks sessions, leases and the worker again under the locks session setup takes before it deletes anything. It first clears the Keychain items of idle profiles in the pre-XDG folder, since opening the data migrates that folder and its profiles' items are named from the old paths. When both folders hold data the Engine refuses to open them (`MigrationError`), so nothing can set up a session there either; the zap then checks live sessions again and deletes both folders without purge. Without Homebrew it deletes the zap files itself and names what is left: the app to move to the Trash, or `uv tool uninstall openswap`.

After `rumps` attaches the status item, a short timer steals the click for the popover (`menubar_panel.MenuBarPanel`) and sets autosave name `com.opensoft.openswap.menubar`.

## Split: pure vs AppKit

`menubar_display.py` holds import-safe helpers (`format_title`, `MenuBarSettings`, notification copy, panel snapshot adapters). `menubar.py` is the rumps app and re-exports those helpers. Tests in `tests/test_menubar.py` import `openswap.menubar` and never import AppKit.

`menubar_panel.py` is AppKit-only: popover, bars, Dark Mode colors, `fit_status_item`. The header loads the packaged OpenSoft symbol from `openswap/assets`; the same OpenSoft app icon source is rendered into the widget host's AppIcon catalog.

The header pins the OpenSoft mark and **OpenSwap** name on the left and two bezel-less SF Symbol buttons on the trailing edge (`trailing_header_frames`): **Settings** (`gearshape`) and **More** (`ellipsis.circle`), text fallbacks when the symbol is missing. The footer leads with **Rotate** and **Best** at fixed positions; the **Auto-switch** label plus `NSSwitch` and the provider's **Add account** (ChatGPT also **Review switch** while a switch is pending) pack against the right edge (`trailing_row_frames`); with no cards (empty state, loading, error) there is no footer row at all. Each account card carries a muted **···** button (`ellipsis`) at its top-right, left of the active / sign-in badge; `_CardView.hitTest_` routes every other hit to the card so the row still switches on a click anywhere else. That button pops a per-account `NSMenu` (`_popup_card_menu`, rows from `card_menu_items`): **Rename…**, **Disable** / **Enable**, **Remove…**, reusing the same callbacks the old More submenus used.

The second tab has two identities, decided by Settings → Automation → **Enable ChatGPT switching** (`chatgpt_tab_desktop`; a hint under the switch says which is which). **Off** (the default) it is the **Codex** tab: a card click selects that login for Codex CLI through `_on_account_click` (same confirm and toast as a Claude card), the footer toggle is **Auto-switch** and flips live Codex CLI rotation (`_toggle_codex_auto`, the same path as the Settings row; shown only while Claude auto-switch is on, since the Codex engine rides on that parent engine), the badge says **active**, the card menu says Disable / Enable, API-key rows stay switchable, and there is no shared-roster line or desktop status. **On** it is the **ChatGPT** tab: a card click reopens the ChatGPT app (the guarded experimental path below), the footer toggle is **Suggest switches** (`chatgpt_auto_enabled`), the subtitle reads **Shared with Codex · Codex usage**, the active badge says **shared** (selected in the shared credential file, not a verified ChatGPT session), disabled cards read **(out of rotation)** and the card menu says **Hold out of rotation** / **Back in rotation**, because the disable flag only ever holds a slot out of Codex rotation. `provider_tab_title`, `provider_cards`, `provider_empty_state`, `provider_shared_copy`, `card_badge_text`, `card_title_suffix`, and `card_menu_items` all take `desktop=`. Behavior is `NSPopoverBehaviorApplicationDefined` so More’s overflow menu does not dismiss the popover (Transient would). Click-outside is a global left-click monitor (skip the popover, the status extra, and while More or a card menu is open). Leave-delay `POPOVER_AUTO_CLOSE_S` (12s) starts only after the pointer exits the popover, not on open; the status extra counts as still inside. Rotate / Best / Settings / More / card menus do not close the popover. Settings is an in-popover page (Back returns to the cards) with **General**, **Automation**, and **Remote** sections; More is overflow and, with the popover attached, management only (Claude next-available, Add including Claude and ChatGPT sign-in, Refresh creds, History, Refresh now, Quit). Only when the popover cannot attach does it also carry Claude rotate/best, the desktop submenu, and the Rename / Disable / Remove submenus that list every account. More → Add account → From API key or setup token… opens the in-popover **Add from token** page (`TOKEN_PAGE`): a masked token field with live kind detection (`token_entry_state`), a **Use as API credit for** popup shown only for `sk-ant-api…` keys, an optional email label, and inline sanitized engine errors (`sanitize_token_error`). Cmd+A/C/X/V/Z reach its fields (`forward_edit_shortcut`), and the leave-delay auto-close does not run on this page. The two old modal prompts remain only when the popover cannot attach. The 1s usage tick does not reload Settings, and it does not rebuild the main page on every snapshot (that would swallow a card click). If hold copy changes, `_apply_hold_line` reloads the open main page (or the welcome page, whose account step follows the roster) only, deferred while the left mouse button is down; Settings stays put.

Card title is the alias or org tag (`personal` when the org name is empty); email is the subtitle. A key linked with `add-token --for` is titled **API credit** (its own alias wins) with subtitle `for <parent email>` (the key's own email when the parent row is missing). Sentinel notes (signed-out, foreign credential, …) render even when last-good bars are present. Claude account-row clicks call `switch_to(..., json_output=True)` unless the slot is `USAGE_RELOGIN_REQUIRED`. ChatGPT rows go through `_on_panel_account_click`: parent toggle, capability probe, then the experimental quit/relaunch. A signed-out ChatGPT OAuth row errors instead of opening `claude auth login`. Signed-out Claude clicks never switch a dead backup: capture only when the live Claude login matches that slot’s email **and** org uuid; otherwise the extra runs `claude auth login --claudeai --email` itself (`claude_login.ClaudeLoginRun`, pipes, no TTY, no Terminal window; after confirming if another managed account is signed in). The CLI opens the browser and exits once the OAuth callback lands. The 1s tick drains the result (`_drain_claude_login_result`, ahead of auto-capture): a clean exit whose live login matches the slot captures it and toasts; a clean exit as someone else, a nonzero exit (last output line in the alert), or a 10-minute timeout each alert and leave the card signed out. A matching login that lands some other way still auto-captures on the tick. The Claude page's **Add account** (**Sign in with Claude** on the empty page, whose secondary **Save current login** is `on_add_login`; also **More › Add account › Sign in with Claude…**) starts the same run with no `--email` and slot `None` (`on_add_claude_login`). First `_keep_outgoing_claude_login` refreshes a managed live login's backup in place (the sign-in overwrites its only current refresh token), and confirms instead when the live login is unmanaged or that refresh fails (a Keychain read error or a worker lease stops it outright); a second click, or a signed-out card click, cancels and replaces it. The drain sends it to `_finish_claude_add`: a clean exit with a live login calls `add_account(slot=None)` (new slot for an unknown identity, in-place refresh for a known one) and toasts `{email} added`, or `{name} is already added` when `current_account_number` found a slot (that slot is marked captured so auto-capture does not repeat it); a nonzero exit, a timeout, or no live login each alert. Capture ends in `refresh_async`, which republishes the widget snapshot; a refresh requested while one is in flight is re-run by the next tick (`_refresh_pending`) rather than dropped. A real switch toasts, stamps `autoswitch_state.json` `lastSwitchAt` (engine cooldown, default 5 minutes), and closes. Already-active closes with no toast. A `ClaudeSwitchError` leaves the popover open and brings the extra forward before `rumps.alert`. Cards implement `acceptsFirstMouse_` so the first click on a non-key popover switches. `rebuild_menu` does not reload an open popover (that replaced the view tree mid-click). `_detect_active_change` compares slot number, not email, so two orgs that share an address still refresh.

## Menu-bar display

Settings → General → Menu bar → **Show** selects **Claude**, **ChatGPT**, **Both**, or **Logo only**, independently of the popover tab. Existing settings default to Claude. **Account name**, **5-hour usage**, and **7-day usage** apply to the selected providers; **Claude model limits** appears only when Claude is included. Logo only hides these controls without resetting their saved choices.

`format_menu_bar_title` prefixes each provider and labels quota windows (5h / 7d). Both joins the two provider summaries. ChatGPT uses the selected shared Codex credential, labels its quota **Codex**, and explicitly marks the app identity **unverified**: shared credentials do not prove which account the ChatGPT desktop session is using. Missing shared credentials (including API-key authentication) show **No shared account**, never another saved account. Claude's empty state is **No account**. ChatGPT message limits are not available here.

### Title width

After a successful manual or automatic switch in the extra (including widget
commands and ChatGPT desktop completion), the menu-bar mark's two halves
exchange vertical positions, then flip horizontally back into the original
logo. The sequence takes 1.05 seconds. Account text stays still. Canceled, failed,
already-active, and dry-run switches do not animate. The animation respects
macOS Reduce Motion and coalesces switches that finish together.

`fit_status_item(..., title=...)` writes the optional title on the status-item **button** (rumps still uses the deprecated `NSStatusItem.setTitle_`) and always displays the packaged OpenSoft template image at 16pt. AppKit sizes the image and text together; **Logo only** leaves the logo visible by itself. There is no asterisk preference; legacy `show_icon` values are ignored. Call it after every title rebuild and on popover attach. A sentinel on either provider's active slot still titles from `last_good` (`title_usage`), frozen at that provider's `fetched_at` so a passed weekly reset does not paint as a fresh 0%.

## Appearance

An `NSPopover` shown from a status item inherits the **menu bar** appearance (wallpaper tint), which can stay Aqua while System Settings is Dark. `resolve_popover_theme` prefers `AppleInterfaceStyle` (`Dark` or unset), then `NSApp.effectiveAppearance`.

Palette tokens are catalog `NSColor`s with dynamic providers (`_dynamic`). Draw fills in `drawRect_`. Do not set `CALayer` `CGColor` from PyObjC (logs `ObjCPointerWarning` and does not flip with appearance).

Observe `effectiveAppearance` and `AppleInterfaceThemeChangedNotification`; reload the popover if it is shown.

## Auto-switch from the extra

`MenuBarSettings` is `menubar_settings.json` (title, refresh, Claude auto on/off, ChatGPT switching, ChatGPT suggestions, kickoff). General holds menu-bar display, confirmation, and refresh controls, then **This Mac** (Open at login, see [Process](#open-at-login)); Remote holds the local worker (Remote tasks). Automation names each surface explicitly: **Auto-switch Claude accounts**, **Enable ChatGPT switching**, **Suggest ChatGPT account switches**, and **Auto-switch Codex CLI accounts**. ChatGPT switching defaults off. The suggestions toggle is disabled while the parent is off; suggestions still require their own stored preference and never restart ChatGPT without approval. A legacy file that already had suggestions on and lacks the parent key migrates the parent on; a present `false` always wins. ChatGPT accounts and add/disable/remove stay visible when switching is off; a row click then switches Codex CLI instead (the tab is titled Codex), and only the desktop relaunch itself is refused (controller checks are authoritative).

When switching is on, the extra verifies the ChatGPT app's OpenAI signature and required bundle shape, then probes its bundled Codex backend against a disposable file-backed credential home. It also applies the transaction’s complete Codex configuration policy on a worker whenever the ChatGPT view is active and the observation is stale: never codesign, backend probing, or process inspection on the AppKit thread. Routine signed app updates remain available when this capability contract passes; known-incompatible builds can be blocked. Typed states are `checking`, `unsupported`, `missing`, `invalid`, `stopped`, and `running`. A fresh stopped observation uses **Switch and open ChatGPT**; a fresh running observation uses **Restart ChatGPT**. Running/stopped observations and retryable operational probe failures expire after five seconds. Installation, process state, selected credentials, and relaunch do not verify the profile ChatGPT actually loaded.

ChatGPT suggestions use Codex quota. They cannot run with live Codex CLI rotation; the Codex control is disabled with an explanation while both ChatGPT switching and suggestions are on. The threshold and next-account strategy form one **Shared rotation policy** in `settings.json` via `openswap config`. Cooldown / last switch live in `autoswitch_state.json`. Changing strategy from the extra calls `set_setting` then `_restart_engine` so the running engine reloads policy.

Settings-page strategies: **Most quota left** (`best`), **Burn weekly first** (`consume-first`, ranks 7d `resets_at`), **Burn 5-hour first** (`soonest-5h`, ranks 5h `resets_at`). A muted hint under the picker explains the selected strategy (7-day vs 5-hour when relevant). See `autoswitch._window_reset_ts`. `SwitchEvent.trigger` stays `consume-first` for both consume strategies; that is not the settings key. A muted hold-reason line under the popover header paraphrases the engine's last no-switch or exhausted event (`hold_line_from_event`); the extra does not re-rank cards. When a Claude Code session or IDE lock is live, a muted `running_line` sits above the footer. A live Codex TUI (not `codex exec` or `codex app-server`) adds a second muted `codex_running_line`. Extra Settings can turn Codex rotation off with `autoswitch.codexEnabled` without stopping Claude auto-switch. A successful extra switch (card, Rotate, Best) calls `record_manual_switch` so that policy does not undo the pick for `cooldownSeconds`.

## Kickoff

`kickoff.py` is due/eligibility + `claude -p ok`. The extra owns the clock (`kickoff_hour` / `minute`, `kickoff_last_date`). **Start Claude 5-hour window** and its time live under Settings → Automation; time is an hourly `NSPopUpButton` (`kickoff_time_options`). Persist `kickoff_last_date` only after a successful pass. Skip API-key accounts and windows whose `resets_at` is still in the future.

## Notifications

`rumps.notification` needs a bundle id. In the cask's app that is the bundle's own (`com.opensoft.openswap`). A source install has none, so `ensure_notification_identity` writes a tiny `Info.plist` next to the uv interpreter (`com.opensoft.openswap.menubar`) if missing.

After an experimental ChatGPT desktop switch completes, the extra sends a
silent **ChatGPT reopened** notification asking the operator to check the
selected account. The inline **ChatGPT reopened · Check the profile** status
remains the fallback if notification delivery fails. Consent and error feedback
remain dialogs; completion does not claim that the running profile is verified.

A switch toast includes “Restart Claude Code to apply now, or wait about 30 seconds.” only when a Claude Code session or IDE lock is live (`claude_running`). Otherwise the restart sentence is omitted. Codex switches include “Restart Codex to apply.” only when a Codex TUI is live (`codex_running`).

A slot that newly becomes re-login-needed toasts once (`personal signed out`) when auto-switch is off (the engine already emits `account-quarantined` when it is on). Capture success toasts `{name} is signed in again`.
