# OpenSwap remote execution: provider capability research

Checked 2026-09-27 against official documentation and the installed Codex CLI help. These are documentation findings, not completed integration tests or legal advice. No credentials were inspected and no provider jobs were launched.

## Decision summary

A local worker is technically feasible. Prefer a Codex App Server adapter and a separately designed Claude adapter. Do not assume that an SDK, subscription login, and third-party credential management are interchangeable. The strongest product opportunity is a cross-provider task queue, research workflow, and OpenTag connector: both providers already offer native remote control.

## Codex

- **Lifecycle:** App Server provides JSON-RPC, authentication, history, streamed events and approvals. Key methods are `thread/start`, `thread/resume`, `thread/fork`, `turn/start`, `turn/steer`, and `turn/interrupt`; interruption ends in an explicit interrupted status. `account/read` and `account/rateLimits/read` support readiness and usage reporting. Use stdio locally; remote WebSockets require separate transport authentication and TLS. Do not expose its entire RPC surface: some explicit shell/process methods run outside the agent sandbox. Stable and experimental API fields are distinguished. [App Server](https://learn.chatgpt.com/docs/app-server)
- **Simpler adapter:** `codex exec --json` emits JSONL lifecycle/tool events. It defaults to a read-only sandbox; workspace writes can be enabled explicitly. This is sufficient for an initial one-shot worker, with the application supervising the process and storing output. [Non-interactive mode](https://learn.chatgpt.com/docs/non-interactive-mode)
- **SDK:** `@openai/codex-sdk` supports starting, continuing and resuming local threads. Official guidance positions it for automation, while App Server fits custom clients with approvals and history. The old Codex MCP server has been removed; OpenTag should expose its own worker MCP interface, not depend on that old command. [Codex SDK](https://learn.chatgpt.com/docs/codex-sdk)
- **Billing/auth:** ChatGPT login provides subscription access; API keys charge the API account. API keys are the normal recommendation for programmatic workflows. Enterprise access tokens support trusted automation that needs ChatGPT-managed entitlements. Cached login is refreshed by Codex. File-backed credentials live under `CODEX_HOME`; keyring, automatic and ephemeral storage also exist. CLI/IDE cached login can be shared, so mutating the user's global auth can affect other clients. [Authentication](https://learn.chatgpt.com/docs/auth)
- **Subscription automation is documented, with boundaries:** the advanced guide describes reusing ChatGPT-managed auth on trusted private runners when necessary. Codex itself must refresh and persist the cache. One copy must not be shared across concurrent jobs or multiple machines; restoring an old snapshot loses refreshed tokens. The guide excludes public/open-source repository workflows. This is not evidence of permission for subscription pooling, resale or quota evasion. [Advanced account-auth automation](https://learn.chatgpt.com/docs/auth/ci-cd-auth)
- **Plan availability:** paid Plus/Pro plans explicitly include CLI access; organizational seats and workspace controls also matter. Free/Go desktop availability must not be generalized to CLI eligibility. Limits are shared with other Work/Codex usage; an API fallback changes billing and must be opt-in. [Pricing and feature availability](https://learn.chatgpt.com/docs/pricing)
- **Research:** local Codex offers hosted web search, cached by default and live with `--search` or configuration. Search events appear in JSON output. Hosted search is separate from the sandbox's command-network controls. This supports ordinary sourced research, but does not establish access to every ChatGPT Deep Research feature through the local CLI. [Web search](https://learn.chatgpt.com/docs/web-search)
- **Existing competitor:** Codex Remote already starts tasks on a connected Mac/Windows computer from ChatGPT mobile, streams progress, accepts instructions/approvals and shows diffs. Availability depends on rollout/workspace settings; the host must stay awake and online. [Codex Remote](https://learn.chatgpt.com/docs/remote)

Local evidence: installed CLI reports `codex-cli 0.158.0-alpha.2`. Its help includes `exec`, `app-server`, experimental `remote-control`, `--remote`, `--remote-auth-token-env`, `--search`, sandbox and approval options. This establishes local binary surfaces only; pin and test a supported release before shipping.

## Claude Code

- **Lifecycle:** unmodified `claude -p` supports noninteractive tasks, JSON/stream-JSON output, explicit session IDs and `--resume`. On SIGTERM, Claude Code records a running command as killed and stops new work; resumption accepts a new prompt rather than silently replaying the interrupted turn. Use exact session IDs in a concurrent worker. Headless mode loads project hooks/MCP configuration without an interactive trust prompt; `--bare` can suppress discovery for controlled jobs, but its authentication/feature tradeoffs must be checked in the spike. [Programmatic CLI](https://code.claude.com/docs/en/headless)
- **SDK and research:** Python/TypeScript Agent SDK supplies Claude Code's loop, tools and sessions. Its quickstart uses an API key or supported cloud provider and explicitly disallows offering Claude.ai login/rate limits in third-party products without prior approval. `WebSearch` is a documented tool, enabling sourced research workflows. [SDK overview](https://code.claude.com/docs/en/agent-sdk/overview), [SDK quickstart](https://code.claude.com/docs/en/agent-sdk/quickstart)
- **Critical product boundary:** Anthropic permits hosting/running the unmodified Claude Code binary subject to its Commercial Terms and conditions: preserve built-in authentication options; each user signs in with their own credentials and is billed directly. Separately, third-party developers must not collect, store or intermediate Claude.ai tokens, offer their own Claude.ai login, or route subscription requests for users. Native sign-in to the unmodified binary is explicitly distinguished. Therefore an OpenSwap credential-vault/router and a launcher of the user's own Claude Code are materially different designs. Obtain clarification for the exact OpenTag remote-triggered flow before advertising subscription compatibility; API-key integration is the documented SDK route. [Legal and compliance](https://code.claude.com/docs/en/legal-and-compliance)
- **Isolation:** native Claude login supports Pro/Max and organizational accounts. `CLAUDE_CONFIG_DIR` selects a separate credential-file location and, on macOS, a separate keychain entry. Have the provider binary own login/storage/refresh in that profile; this technical isolation does not override the above product restrictions. API environment variables can affect the effective auth method. [Authentication](https://code.claude.com/docs/en/iam)
- **Existing competitor:** `claude remote-control` now runs a server with on-demand sessions, same-directory or isolated-worktree spawning, and `--capacity` (default 32). It uses outbound HTTPS, supports mobile push for required actions, and is available on eligible Pro/Max/Team/Enterprise subscription accounts, not API keys. Team/Enterprise require admin enablement. Its supported clients are Claude web/mobile; the docs do not establish a public third-party relay API for OpenTag. The capacity setting is a process ceiling, not a promise of quota or guaranteed throughput. [Remote Control](https://code.claude.com/docs/en/remote-control)

## Recommended provider contract and validation gates

These are engineering recommendations inferred from the documented boundaries:

1. Keep one local provider-owned auth context per enrolled account/profile. Pin a job to its profile for its lifetime. Never switch the global auth file while jobs are running. Start with one active job per profile; test higher concurrency deliberately.
2. Implement `probe`, `start`, `resume`, `events`, `interrupt`, and capability flags such as approvals, live research, usage reporting and supported billing mode. Preserve provider session IDs separately from OpenSwap job IDs.
3. Show billing mode before dispatch. Stop or queue when limits/auth fail; never silently buy credits, switch to API billing, rotate to another account, or replay a possibly completed action.
4. Use approved working directories, a fresh worktree for code edits, read-only research tools by default, and a durable waiting-for-user state for approvals. Sandbox enforcement and approval UX are different layers.
5. Test logout/refresh while running, local desktop activity alongside worker activity, crashes, restart/resume, cancellation with child processes, network loss, sleep/wake and quota exhaustion. Same-profile concurrency and provider-version compatibility remain unverified.
6. Keep provider secrets off the relay. Pair OpenTag to the worker using separate device credentials; expose narrowly scoped task actions rather than arbitrary shell/RPC access.

Product recommendation: ship an optional worker module under OpenSwap first, behind a provider-neutral protocol. OpenTag supplies orchestration. A later standalone server can reuse that module when there is demand from users who do not need OpenSwap account management. The provider findings do not by themselves justify a separate brand or repository.
